# ADR 0007 — Course adapter 의 실패 표면을 둘로 나눈다

상태: ACCEPTED
작성일: 2026-10-02
관련 Gate: Gate 3

## 맥락

Gate 3 Contract v1 은 강좌 단건을 이렇게 정의한다.

| 상황 | HTTP | 본문 |
|---|---|---|
| 정상 | 200 | `{ v: 1, item: Course }` |
| 없는 강좌 | 404 | `{ v: 1, error: "not_found" }` |
| 잘못된 id | 400 | `{ v: 1, error: "invalid_id" }` |
| Bridge 장애 | 503 / HTML / 302 | 보장 없음 |

"없음"과 "장애"가 **HTTP 상태로 분리**됐다. Gate 1 draft 는 둘을 `item: null` 하나로 뭉갰기 때문에
adapter 가 구분할 수 없었다.

그런데 실패를 어떻게 돌려줄지에 대해 두 요구가 서로 다른 답을 원한다.

1. **AGENTS.md §6.4**: "Bridge 실패는 예외가 아니라 상태다. 페이지가 깨지거나 에러 화면이 뜨면 안 된다."
   → 실패를 `unavailable` 상태로 돌려줘야 한다.
2. **ISR 의 동작**: 강좌 페이지는 `revalidate` 로 재생성된다. 재생성 중 데이터 함수가 **throw 하면**
   Next 는 새 HTML 을 만들지 않고 **마지막으로 성공한 HTML 을 계속 내보낸다.**
   여기서 `unavailable` 을 돌려주면 그 상태가 성공으로 간주되어, 잘 만들어 둔 강좌 페이지가
   "일시적으로 볼 수 없습니다" 화면으로 **덮인다.** Bridge 가 1분 흔들렸을 때 치르는 대가가
   "캐시된 좋은 페이지를 잃는 것"이 된다.

즉 ISR 로 렌더하는 페이지에서는 throw 가 사용자에게 **더 좋은** 결과를 준다.
반대로 캐시본이 없는 첫 빌드나, 페이지의 일부분만 강좌에 의존하는 경우에는 throw 가 전체를 깨뜨린다.

## 결정

한쪽을 고르지 않고 **표면을 둘로 나눈다.** 둘 다 `@/legacy/server` 에서 공개한다.

| 함수 | 없는 강좌 | 실패 | 쓰는 곳 |
|---|---|---|---|
| `getCourse(id)` / `getCourses()` | `null` / `[]` | `BridgeError` **throw** | ISR 로 렌더하는 강좌 페이지 |
| `getCourseState(id)` / `getCoursesState()` | `{status:'missing'}` / `ready` + `[]` | `{status:'unavailable'}` | 캐시본이 없을 수 있는 곳, 페이지의 일부 섹션 |

mock adapter 도 **같은 규약**을 따른다. `?course=error` 는 mock 에서도 `BridgeError` 를 던지고,
`?course=missing` 은 `null` 이다. 그래서 mock 과 http 를 바꿔 끼워도 호출자 코드가 같다.

`getCourseState` 는 `BridgeError` **만** 삼킨다. 그 밖의 예외(예: Contract 를 벗어난 fixture 때문에
zod 가 던진 것)는 다시 던진다. Bridge 장애와 우리 쪽 버그를 같은 화면으로 덮으면 버그가 조용히 배포된다.

## 이유

- AGENTS.md §6.4 가 지키려는 **실질**("사용자가 깨진 화면을 보지 않는다")은 ISR 경로에서
  오히려 throw 가 더 잘 지킨다. 조문을 글자대로 따르면 그 실질을 잃는다.
- 404 를 `null` 로 돌리는 것은 상태가 아니라 **사실**이다. 없는 강좌는 장애가 아니므로
  `unavailable` 과 섞으면 안 된다 (그래야 페이지가 404 메타데이터를 낼 수 있다).
- 어느 쪽을 쓸지는 **렌더 전략을 아는 호출자**가 결정해야 한다. adapter 가 미리 정할 수 없다.

## 대안

- **`unavailable` 만 돌려준다 (Gate 1 방식):** 기각. ISR 재생성 실패 때마다 캐시된 좋은 페이지가
  에러 화면으로 덮인다. Bridge 가 잠깐 흔들리는 것이 사용자에게 보이는 사고가 된다.
- **throw 만 한다:** 기각. 캐시본이 없는 첫 빌드에서 Bridge 가 죽어 있으면 페이지가 아예 뜨지 않는다.
  홈처럼 강좌가 한 섹션일 때도 전체를 깨뜨린다.
- **`Result<T, E>` 한 가지 표면:** 기각. 모든 호출지에서 분기를 강제하지만, ISR 이 "마지막 성공본 유지"를
  하려면 결국 throw 가 필요하다. 표면은 하나가 되고 ISR 이익은 사라진다.

## 결과

- 장점: 호출자가 렌더 전략에 맞는 표면을 고를 수 있다. 404 와 장애가 섞이지 않는다.
- 비용: 공개 함수가 2개 → 4개로 늘었다. 어느 것을 쓸지 고르는 부담이 호출자에게 생긴다.
  그래서 `adapters/course/index.ts` 주석과 이 ADR 에 선택 기준을 적어 둔다.
- `AGENTS.md` §6.4 의 문구("Bridge 실패는 예외가 아니라 상태다")와 `getCourse` 의 동작이
  글자 단위로 어긋난다. **사람이 §6.4 에 ISR 예외를 명시할지 결정할 잔여 항목이다.**

## 재검토

Gate 8 에서 강좌 상세 페이지를 실제로 만들 때, 두 표면이 모두 쓰이는지 본다.
한쪽이 끝까지 안 쓰이면 그때 지운다.
